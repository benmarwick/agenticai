# Agent Coordination Protocol

This file is the coordination contract for every agent working on this
repository. Read it before touching any shared file. It applies regardless of
which agent tool, session, or CLI instance started the work.

Coordination state lives in `CLAIMS/` (one claim per file). To work on a shared
file you must first claim it; while a claim exists, no other agent may edit that
file. This prevents the collision you saw earlier, where two agents edited
`analysis/paper/paper.qmd` within minutes of each other.

## Scope

- **Shared files that require a claim before editing:** every file tracked in
  git or produced by tooling, including `analysis/paper/paper.qmd`,
  `analysis/paper/references.bib`, `README.qmd`, `DESCRIPTION`, `.gitignore`,
  `AGENTS.md`, and anything under `analysis/data/`.
- **Files that do not require a claim:** your own scratch notes outside
  tracked paths (for example a `notes/` directory you are not committing),
  transient tool output, and `paper.docx`/`paper_files/` regenerated by
  rendering. Rendering is not editing.

## The claim protocol

A claim is a directory named after the file or path you own:

```
CLAIMS/analysis--paper--paper.qmd/
```

Nested separators are `--` (two hyphens), and any `/` in the path becomes `--`.
Use `mkdir` to take the claim; `mkdir` is atomic, so a claim can never be taken
by two agents at once:

```bash
# take a claim (fails if someone else owns the file — wait or negotiate)
mkdir CLAIMS/analysis--paper--paper.qmd

# write the claim metadata immediately after mkdir succeeds
cat > CLAIMS/analysis--paper--paper.qmd/claim.txt <<'EOF'
path: analysis/paper/paper.qmd
claimed_by: <your agent name / session id>
task: <one line: what you will change>
claimed_at: <UTC timestamp>
done_status: in_progress
EOF
```

While the claim exists you have exclusive write access to that path. Do not
touch the file without a claim:

```bash
# could a claim for this target be taken?
find CLAIMS -maxdepth 1 -type d -name 'analysis--paper--paper.qmd'
```

When you finish:

```bash
# update status and release
sed -i '' 's/^done_status: .*/done_status: done/' CLAIMS/analysis--paper--paper.qmd/claim.txt
rm -rf CLAIMS/analysis--paper--paper.qmd
```

If another agent holds the claim you need:

1. Read `CLAIMS/<target>/claim.txt` to see what they are doing.
2. Wait, ask the lead agent/session, or pick a different task. Do not bypass a
   claim.

## Rules

1. **Claim before you edit.** Never modify a shared file without holding its
   claim. `mkdir` the claim, write `claim.txt`, then edit.
2. **One claim per target.** Multiple claims for different targets are fine and
   normal.
3. **Release when done.** Remove the claim directory only after your file
   changes are written. If you are interrupted, leave the claim in place with a
   note in `done_status:` so the next agent can recover your context.
4. **Claim `AGENTS.md` too.** This coordination file is itself a shared file;
   an agent revising it must hold `CLAIMS/AGENTS.md` while editing.
5. **Never edit other agents' uncommitted work.** If `git status` shows changes
   on a file you were about to edit and the claim says `done`, the owner is mid-
   commit. Wait.

## Delegate, do not duplicate

When the same logical task appears in two places, one agent does the work and
the other reviews. The pipeline skills in this environment
(`deep-research`, `academic-pipeline`, `academic-paper-reviewer`) already stage
production and review; run one pipeline at a time, do not run two sessions of
the same pipeline against the same files.

## Audit commands

```bash
find CLAIMS -maxdepth 1 -type d   # list active claims
find CLAIMS -name claim.txt -exec cat {} \;   # show all claim metadata
```

## Project context (rrtools compendium)

This is an rrtools research compendium named `agenticai`, anchored at this
directory. Renv is the package environment: run R via the project (`renv::restore()`
if the library is missing, never modify `renv.lock` without a claim). Render
the paper with:

```bash
quarto render analysis/paper/paper.qmd
```

Edit the manuscript (`analysis/paper/paper.qmd`) and the README
(`README.qmd`) rather than their rendered outputs (`paper.docx`, `README.md`).

## Zotero library access

Read and write a Zotero library from the shell with the `zotero-cli` command - search papers by keyword or meaning, read PDF full text and page ranges, get and set metadata, manage collections, tags, notes and annotations, add items by DOI/URL/ISBN, and export bibliographies. Use whenever the user asks about their Zotero library, references, citations, papers they have saved, or their reading notes.

Read `.agents/skills/zotero-cli/SKILL.md` before using it. Prefer it over the Zotero MCP server when you have shell access: the MCP tool schemas cost ~13k tokens of context on every request, this costs only what you run.

Quick check that it is set up: `zotero-cli config`. Pass `--json` whenever you will parse the output.

# Open ScholarPeer — Always-On Rules

These rules apply automatically in any project where Open ScholarPeer is installed.

## Brain protocol (apply on every invocation)

1. **Read `.brain/session.json` first** to understand current state.
2. **Load only the artifacts in the active step's `reads:` contract** (see `docs/ARTIFACT_CONTRACTS.md`). Do not load the full `.brain/` directory.
3. **After completing a step, update `session.json`:** set the matching `phases.<name>` block to `completed`, set `completed_at`, and update `resume_from`.
4. **Re-runs overwrite with a warning.** If a step is already `completed`, print one warning, then proceed.

## Persona discipline

- Each numbered command (`/N-osp-*`) activates exactly one persona skill (`osp-<name>-agent`). Do not blend personas.
- The Q&A engine (`/5-osp-qa`) uses two personas at once: Query Agent (main thread) and Answer Generator (subagent, or self-reflection on tools that lack subagents).
- The orchestrator (`osp-orchestrator`) never performs review work — it only routes.

## Subagent vs self-reflection

- **Prefer subagents** for the Q&A engine on tools that support them — every supported tool except the two named below.
- **Fall back to self-reflection** with strict turn markers (`=== Query Agent === ... === END === === Answer Generator === ...`) where subagents are unavailable — always on Mistral Vibe and OpenHands, and on any tool where the delegation call does not work. Finishing the phase in the weaker mode beats stopping it; note which mode was used in the artifact.
- Self-reflection is a documented weaker substitute. See `KNOWN_LIMITATIONS.md`.

## User orientation (required on every phase invocation)

Before doing any work in a phase, print a short orientation block so the user always knows where they are:

```
── <Phase name> ──────────────────────────────────────────
What this phase does: <one sentence — the agent's role and why this step exists>
Reads:  <list the key input files>
Writes: <list the key output files>
Effort: <rough estimate — "~2 min, ~N tool calls", etc.>
──────────────────────────────────────────────────────────
```

After the phase completes, the closing report block must say **what was done** (findings, counts, highlights), not just which command to run next. The user is learning the system as they go — orient them every time, even on repeat runs.

## Output discipline

- Every `.brain/raw/*.md` file uses the universal artifact structure: `## Method`, `## Output`, `## Provenance`.
- Reports describe what was done — they are not raw transcripts of tool calls.
- Citations must trace back to retrieved literature; do not invent them.

## File references in user-facing output

- When mentioning a `.brain/` artifact in a report or reply, use the vendor-provided native file reference format for your tool:
  - Claude Code / Cursor / Gemini CLI / Codex CLI / Qwen Code / OpenCode / Junie / Kiro: `@.brain/raw/01_summary.md`
  - Copilot CLI: `#file:.brain/raw/01_summary.md`
  - Kimi Code / Mistral Vibe / OpenHands / Antigravity: plain path (no native shorthand)
- Always pair the native reference with the `↳ .brain/…` path in the terminal report block so users can locate files regardless of tool.

## File ownership

- `.brain/` is gitignored — never commit it.
- `.open-scholar-peer/` (MCP server + venv) is gitignored — never commit it.
- Tool-specific config files (`.mcp.json`, `.claude/`, etc.) at project root are user-editable.
- Adapter content under `extensions/.{tool}/` in this repo is **generated by the sync script** — edit `extensions/_shared/` instead and re-run `scripts/sync_adapters.py`.
